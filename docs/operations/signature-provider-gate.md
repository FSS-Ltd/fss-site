## Exact access and evidence needed before passing the gate

- [ ] User identifies chosen provider and existing sandbox/production account owner, or explicitly chooses to provision an account. No provider has been selected by this research.
- [ ] Identify where account access is already configured. Supply secret **locations/names only**, not secret values in chat, source control or this report.
- [ ] For a Docusign JWT candidate: sandbox account ID, authorized sending user GUID, integration/client ID, auth environment, configured redirect URI, secure RSA private-key location and completed consent. Verify sender permission and authenticated API base URI from the account.
- [ ] Account admin access to inspect Connect/API entitlement and configure an HTTPS test listener and HMAC key; secure HMAC secret location. Identify an approved test document and controlled test signers before any sends.
- [ ] Account-specific production quote/order evidence explicitly covering this workflow, API/Connect entitlement and Go-Live requirements; actual account region and applicable DPA/retention evidence.

## Account tests not performed

- [ ] Authenticate; send the exact approved revision; verify signer ordering and recipient identity matching.
- [ ] Receive genuine HMAC callback; reject altered body, wrong key, missing signatures and wrong account/envelope; handle replay and out-of-order delivery without repeated side effects.
- [ ] Partial signing cannot advance agreement or Growth state; all required signers complete, authoritative API status agrees, signed PDF and audit certificate download and are retained privately before recording completion once.
- [ ] Edited-after-approval content and signer changes invalidate approval. Replacement prevents a delayed old-envelope completion from advancing the new revision.
- [ ] Declined, expired and voided envelopes remain non-signed; test cancellation/completion race and provider errors with controlled recipients.
- [ ] Evidence retrieval failure is recoverable without prematurely recording signed state. Repeated completion invokes the existing Growth won/outreach-stopping boundary once and preserves historical terminal deals.
- [ ] Keyboard/screen-reader signing journey and document readability pass; actual region, retention and contractual processing terms match FSS requirements.

At the time of this research, the managed-provider path was blocked on provider/account input and actual capability evidence. The user subsequently approved in-house signing, so this historical provider gate no longer blocks Task 9. Public documentation alone still does not establish account entitlement or authorize a purchase.

## Repository and configuration findings

The project and isolated worktree environment files contain no signing-provider variable names. A read-only listing of the linked FSS Vercel project also found no signing-provider variable names; no environment values were displayed. Provider selection and the location of sandbox access were requested from the user. Their existing authorization to push and merge all build PRs remains valid.

The Growth integration boundary is `lib/growth/pipeline/transition-engagement.ts`: it locks an engagement, returns `alreadyApplied` for the same state, checks the expected version and permitted transition, then records the stage event, stops active outreach and appends audit evidence in one transaction. `stages.ts` keeps won/lost terminal. Managed signature completion must preserve those rules and establish an explicit authorized service identity; it must not forge founder context or rewrite terminal history. This is an implementation constraint identified by code inspection, not implemented Task 9 behavior.
